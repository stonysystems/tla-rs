### 1. Spec Layer: 11 Atomic Actions

`raft.rs` defines 11 atomic state transitions for the Raft protocol. Each is an independent, minimal-granularity operation:

| Spec Function | Purpose | Sends |
|---------------|---------|-------|
| `LInit` | Initialize state (Follower, term=0, empty log) | — |
| `LTimeout` | Follower/Candidate starts an election | RequestVote |
| `LGrantVote` | Grant vote to a candidate | VoteResponse |
| `LReceiveVoteGranted` | Record a received vote | None |
| `LBecomeLeader` | Vote count reaches quorum, become Leader | None |
| `LClientRequest` | Leader appends client request to log | None |
| `LSendAppendEntries` | Leader sends AppendEntries to follower | AppendEntries |
| `LFollowerAppendEntries` | Follower processes AppendEntries | AppendResponse |
| `LHandleAppendResponse` | Leader processes successful AppendResponse | None |
| `LHandleAppendReject` | Leader processes failed AppendResponse (backtrack next_index) | None |
| `LAdvanceCommitIndex` | Leader advances commit_index | None |
| `LStepDown` | Discover higher term, revert to Follower | None |

`LNext` is a disjunction of these 11 actions, each appearing independently:

```rust
pub open spec fn LNext(s: LState, s_: LState, c: LConstants) -> bool {
    ||| exists |sent_packets| LTimeout(s, s_, c, sent_packets)
    ||| exists |...| LGrantVote(s, s_, c, ...)
    ||| exists |...| LReceiveVoteGranted(s, s_, c, ...)
    ||| exists |sent_packets| LBecomeLeader(s, s_, c, sent_packets)
    ||| exists |...| LClientRequest(s, s_, c, ...)
    ||| exists |...| LSendAppendEntries(s, s_, c, ...)
    ||| exists |...| LFollowerAppendEntries(s, s_, c, ...)
    ||| exists |...| LHandleAppendResponse(s, s_, c, ...)
    ||| exists |...| LHandleAppendReject(s, s_, c, ...)
    ||| exists |...| LAdvanceCommitIndex(s, s_, c, ...)
    ||| exists |...| LStepDown(s, s_, c, ...)
}
```

**Key characteristic**: each atomic action has strict preconditions (guards) and does not handle the "receive a message, check its term, then decide what to do" logic.

### 2. Generated Code Layer: 12 Verified Exec Functions

`raft_gen.rs` is auto-generated by the transpiler from the spec. Each spec action maps to one exec function:

```
CInit, CTimeout, CGrantVote, CReceiveVoteGranted, CBecomeLeader,
CClientRequest, CSendAppendEntries, CFollowerAppendEntries,
CHandleAppendResponse, CHandleAppendReject, CAdvanceCommitIndex, CStepDown
```

Each function is Verus-verified, with ensures clauses guaranteeing the exec implementation precisely satisfies the spec predicate:

```rust
pub exec fn CGrantVote(s: &CState, c: &CConstants, ...) -> (result: (CState, Vec<CRaftMessage>))
requires
    s.valid(), c.valid(),
    (*candidate_term >= s.current_term),           // precondition
    (!s.has_voted || s.voted_for == *candidate_id),
ensures
    result.0.valid(),
    LGrantVote(s@, result.0@, c@, ...),            // precisely satisfies spec
```

**Verification status**: 0 assumes, 3 external_body (clone helpers only), all 12 business functions fully verified.

### 3. Host Layer: 978 Lines of Unverified Protocol Logic

**This is the core problem Phase 27 addresses.**

host.rs contains 19 functions with substantial **unverified protocol logic** — not simple I/O glue code, but substantive Raft protocol decisions:

#### 3.1 Step-Down + Guard Logic in Message Handlers (Unverified)

Every message handler manually implements the "receive message -> check term -> step down -> check guards -> call atomic function" flow. Consider `handle_request_vote` (~85 LOC):

```rust
fn handle_request_vote(&mut self, config, src, term, candidate_id, ...) -> StepResult {
    // 1. Hand-written step-down logic (UNVERIFIED)
    if term > self.state.current_term && term < u64::MAX {
        let (new_state, _sent) = raft_gen::CStepDown(&self.state, &config.constants, &term);
        self.state = new_state;
        self.last_heartbeat = std::time::Instant::now();
    }

    // 2. Hand-written guard checks (UNVERIFIED)
    if term < self.state.current_term { return no_op; }
    if self.state.has_voted && self.state.voted_for != candidate_id { return no_op; }

    // 3. Hand-written log-up-to-date check (UNVERIFIED)
    let my_last_log_term = if self.state.log.len() == 0 { 0 } else { self.state.log[...].term };
    let log_ok = last_log_term > my_last_log_term || ...;
    if !log_ok { return no_op; }

    // 4. Call the verified atomic function
    let (new_state, _sent) = raft_gen::CGrantVote(&self.state, &config.constants, ...);
    self.state = new_state;

    // 5. Hand-written message construction (UNVERIFIED) — ignores _sent!
    StepResult { outbound: Send { msg: RaftMessage::VoteResponse { term: ..., granted: true, ... } } }
}
```

**Problem 1**: Steps 1-3 are unverified protocol logic. If a guard check is wrong (e.g. `<` instead of `<=`), Verus will not flag it.

**Problem 2**: Step 5 manually constructs the network message, **completely ignoring `_sent`** (the verified message list returned by the generated function). This means even if the spec correctly describes what should be sent, the host may send a different message.

#### 3.2 Composite Actions (Unverified)

`handle_vote_response` (~73 LOC) composes multiple atomic operations:

```rust
fn handle_vote_response(&mut self, config, term, granted, voter) -> StepResult {
    // step-down (UNVERIFIED)
    if term > self.state.current_term { CStepDown(...); return; }

    // guard checks (UNVERIFIED)
    if !is_candidate { return; }
    if !granted { return; }
    if !servers.contains(voter) { return; }

    // call CReceiveVoteGranted (VERIFIED)
    let (new_state, _) = CReceiveVoteGranted(...);
    self.state = new_state;

    // quorum check + become leader (UNVERIFIED composition)
    if votes.len() >= quorum_size {
        let (new_state, _) = CBecomeLeader(...);
        self.state = new_state;
    }
}
```

The `CReceiveVoteGranted` -> check quorum -> `CBecomeLeader` composition is unverified.

#### 3.3 Commit Index Scan (Unverified)

`try_advance_commit_index` (~70 LOC) manually implements quorum counting:

```rust
fn try_advance_commit_index(&mut self, config) -> StepResult {
    let mut n = self.state.log.len() as u64;
    while n > self.state.commit_index {
        if self.state.log[(n-1) as usize].term == self.state.current_term {
            let mut count: u64 = 1; // count self
            for j in 0..config.peers.len() {
                if let Some(mi) = self.state.match_index.get(&(j as u64)) {
                    if *mi >= n { count += 1; }
                }
            }
            if count >= config.constants.quorum_size {
                let (new_state, _) = CAdvanceCommitIndex(&self.state, &config.constants, &n);
                self.state = new_state;
                break;
            }
        }
        n -= 1;
    }
}
```

This O(log_len * num_peers) scan is entirely unverified.

### 4. Root Cause Analysis: Spec Granularity vs. Host Responsibility Mismatch

The root cause is that **the spec's atomic action granularity is too fine**, mismatching the actual message-handling flow:

```
Receive a RequestVote message
  -> Real flow: step-down-if-needed -> check guards -> grant-vote-or-noop
  -> Spec model: LStepDown (independent action) + LGrantVote (independent action)
  -> Host must manually orchestrate the composition of these two independent actions
```

This creates a **verification gap**:

```
+-------------------------------------------------------+
|               VERIFIED (Verus)                        |
|  LStepDown -> CStepDown    LGrantVote -> CGrantVote   |
|  (verified alone)          (verified alone)           |
+-----------+----------------------------+--------------+
            |                            |
   +--------v----------------------------v---------+
   |              UNVERIFIED (host.rs)             |
   |  if term > current_term { CStepDown() }      |
   |  if guard1 { return noop }                    |
   |  if guard2 { return noop }                    |
   |  CGrantVote()                                 |
   |  manually construct VoteResponse message      |
   +-----------------------------------------------+
```

**Verified**: the state transition within each atomic function is correct.
**Unverified**: when to call which function, whether guard conditions are correct, whether the composition order is correct, whether the sent messages match the spec.

### 5. Comparison: How RSL Does It

RSL does not have this problem because its spec directly models the complete message-handling flow:

```rust
// RSL spec has full message dispatch
pub open spec fn LReplicaNextProcessPacketWithoutReadingClock(s, s_, ios) -> bool {
    match ios[0]->r.msg {
        RslMessage1a{..} => LReplicaNextProcess1a(s, s_, ios[0]->r, sent_packets),
        RslMessage1b{..} => LReplicaNextProcess1b(s, s_, ios[0]->r, sent_packets),
        ...
    }
}

// Each RSL handler directly calls sub-module functions + reconstructs struct
pub open spec fn LReplicaNextProcess1a(s, s_, received_packet, sent_packets) -> bool {
    &&& LAcceptorProcess1a(s.acceptor, s_.acceptor, received_packet, sent_packets)
    &&& s_ == LReplica { acceptor: s_.acceptor, proposer: s.proposer, ... }
}
```

The RSL transpiler generates `CReplicaNextProcessPacket`, `CReplicaNextProcess1a`, etc. — complete message-handling functions. RSL's host.rs only needs to call a single function. RSL's host never manually checks guards or composes multiple atomic operations.

### 6. Summary: What Phase 27 Addresses

| Dimension | Before Phase 27 | Goal |
|-----------|----------------|------|
| **Unverified protocol logic** | ~634 LOC in host.rs | Move into spec, generate verified code via transpiler/manual_code |
| **Message construction** | Host constructs manually, ignores `_sent` from gen functions | Use verified `sent` messages returned by generated functions |
| **Guard correctness** | Hand-written in host, may contain bugs | Defined in spec, executed by verified exec code |
| **Composite actions** | Host manually orchestrates CStepDown + CGrantVote | Defined as composite spec, implemented by verified exec code |
| **Host responsibility** | Protocol logic + I/O + timers | I/O + timers only (~200 LOC) |
| **Verification coverage** | Atomic function internals only | Complete message-handling flow |

**The core value of Phase 27**: extend the verification boundary from "individual atomic operation internals" to "complete message-handling flows", eliminating the verification gap between spec and host.
