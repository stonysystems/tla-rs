# TLA+ Input Compatibility Report

**Date:** 2026-02-19 (Phase 16.8.7)

## Summary

The tla-rs transpiler's TLA+ parser (`translate-tla` / D1 direction) was tested against three corpora:

| Corpus | Total Specs | D1 Parse Pass | D1 Parse Fail | Pass Rate |
|--------|-------------|---------------|---------------|-----------|
| Internal examples (`tests/tla_examples/`) | 7 | 7 | 0 | 100% |
| LLM-authored (`generated_tla_by_llm/`) | 12 | 3 | 9 | 25% |
| Community canonical (`tla_by_community/`) | 4 | 3 | 1 | 75% |
| **Total external** | **16** | **6** | **10** | **37.5%** |

**Key finding:** The parser handles the TLA+ subset generated by our own D3 emitter perfectly (33/33), and handles our curated test examples (7/7). However, it fails on 62.5% of externally-authored TLA+ specs due to unsupported standard TLA+ constructs.

## Unsupported TLA+ Constructs

### Category 1: Range Operator (`..`)

**Pattern:** `1..N`, `0..MaxVal`
**Error:** "Unexpected token in" or "Expected Colon, found"
**Impact:** 5/10 external failures
**TLA+ usage:** Extremely common for defining integer domains

The `..` (DotDot) token is recognized by the lexer but not handled as a binary expression operator in the parser.

### Category 2: Temporal Formula Subscripts (`_<<vars>>`)

**Pattern:** `[][Next]_<<var1, var2, ...>>`
**Error:** "Expected DefEq, found"
**Impact:** 3/10 external failures
**TLA+ usage:** Standard in `Spec ==` temporal properties

The `Spec == Init /\ [][Next]_<<vars>>` pattern defines stuttering equivalence. The parser recognizes `[]` but doesn't handle the `_<<tuple>>` subscript notation.

### Category 3: Record Set Constructors

**Pattern:** `[type : {"Prepared"}, rm : RM]`
**Error:** "Expected RBracket, found"
**Impact:** 1/10 external failures
**TLA+ usage:** Standard for defining message types

Record set constructors use `:` for field-to-set mappings, which conflicts with the parser's record value syntax using `|->`.

### Category 4: Named ASSUME Statements

**Pattern:** `ASSUME QuorumAssumption == ...`
**Error:** "Unexpected token in"
**Impact:** 1/10 external failures
**TLA+ usage:** Common in specs with constant constraints

The parser recognizes `ASSUME` as a keyword but only handles `ASSUME expr`, not `ASSUME Name == expr`.

### Category 5: Constructs That Parse But Don't Generate

These TLA+ constructs are accepted by the parser but produce empty or incomplete Verus output:

| Construct | Example | Status |
|-----------|---------|--------|
| `CHOOSE` | `CHOOSE v \in S : P(v)` | Parsed, not translated |
| `LET...IN` (complex) | `LET x == expr IN body` | Partially supported |
| Function mapping | `[f \in S \|-> expr]` | Parsed via `EXCEPT` path, limited translation |
| Multi-variable `\E` | `\E x \in A, y \in B : P` | Parser handles, codegen drops |
| `IF...THEN...ELSE` | Standard conditional | Supported in some contexts |
| `RECURSIVE` | Recursive operator defs | Not supported |
| `INSTANCE` | Module instantiation | Not supported |
| `LAMBDA` | Anonymous functions | Not supported |

## Recommendations

### High-Impact Parser Improvements (ordered by external failure count)

1. **Range operator (`..`)** — 5 failures. Add `DotDot` as infix binary operator producing `IntRange(lo, hi)` AST node.
2. **Temporal subscript (`_<<...>>`)** — 3 failures. Add subscript notation to temporal formula parsing (even if ignored for spec generation).
3. **Record set constructors** — 1 failure. Distinguish `[field : Set]` from `[field |-> value]` in bracket expression parsing.
4. **Named ASSUME** — 1 failure. Accept `ASSUME Name == expr` as operator-like definition.

### Output Quality Improvements

5. **Function mapping translation** — Community specs (Paxos, Raft, EPaxos) all use `[f \in S |-> e]` extensively. Translating these to `Map::new(|k| ...)` or similar Verus constructs would dramatically improve output for canonical specs.
6. **CHOOSE translation** — Map to Verus `choose` or `let` with postcondition.
7. **Multi-variable quantifier codegen** — Nested `exists` generation for `\E x, y : P`.

## Test Coverage
