# Direct Prior Art: Text -> TLA+

## Summary Finding

As of February 2026, no published paper, repository, or system directly performs end-to-end natural-language-to-TLA+ specification generation. The search protocol (13 searches, 135 results screened, 36 candidates kept) found no work where free-form text goes in and a machine-checkable TLA+ module comes out.

The closest works fall into three categories: (1) code -> TLA+ generation, (2) LLM-assisted TLA+ proof/annotation, and (3) TLA+-focused benchmarks and linting.

## Direct Works (close but not NL->TLA+)

### D1: Specula -- Code -> TLA+ Specification (2025)

- **What it is**: Open-source framework that derives TLA+ specifications from source code (not natural language). Won 1st place in the 2025 TLAi+ Challenge (TLA+ Foundation / NVIDIA).
- **Input**: Source code (Go for etcd Raft, Rust for Asterinas SpinLock)
- **Output**: TLA+ specifications
- **Machine-checkable?**: Yes -- uses trace validation to semantically align spec and implementation
- **Method**: LLM-based generator + Control Flow Analyzer for syntactic/structural correctness + trace validation
- **Source available?**: Open-source (presented at TLA+ Community Meeting, Nov 2025)
- **Evaluation**: Demonstrated on etcd Raft and Asterinas. Trace-based conformance checking.
- **Claim verification**:
  - Claims: Automatically derives TLA+ specs from source code with syntactic+semantic correctness
  - Demonstrated: Working framework on two real systems with trace validation
  - Missing for our use: Takes code not text as input. No NL understanding component. Would need an NL->code->TLA+ two-stage pipeline.

### D2: SysMoBench -- TLA+ System Modeling Benchmark (2025)

- **What it is**: Benchmark for evaluating AI's ability to formally model complex real-world systems in TLA+
- **Input**: System artifacts (source code, documentation, design docs)
- **Output**: TLA+ specifications (generated by LLMs/agents being evaluated)
- **Machine-checkable?**: Yes -- automated evaluation metrics including syntactic correctness, runtime correctness, conformance to system code, invariant correctness
- **Method**: Prompting LLMs directly, few-shot learning, or agentic techniques with external tools
- **Source available?**: Yes -- arXiv:2509.23130, benchmark publicly available
- **Evaluation**: 11 system artifacts (Raft/etcd, Redis, ZooKeeper, Asterinas OS)
- **Claim verification**:
  - Claims: First TLA+-specific benchmark for AI system modeling with automated evaluation
  - Demonstrated: Benchmark with automated metrics on real systems
  - Missing for our use: Input is system artifacts/code, not free-form NL. Benchmark evaluates code->TLA+ not text->TLA+. But evaluation metrics are directly transferable.

### D3: TLA+ Proof Automation with LLMs (2024)

- **What it is**: LLM-guided approach to TLA+ proof automation via recursive decomposition
- **Input**: TLA+ claims/specifications needing proofs
- **Output**: TLA+ proof structures (decomposed sub-claims)
- **Machine-checkable?**: Yes -- each decomposition step is verified
- **Method**: LLMs recursively break complex claims into simpler sub-claims
- **Source available?**: arXiv:2512.09758
- **Claim verification**:
  - Claims: LLMs can guide recursive decomposition of TLA+ proofs
  - Demonstrated: Proof decomposition with verification of each step
  - Missing for our use: Not specification generation. Proves existing specs. But demonstrates LLM understanding of TLA+ semantics.

### D4: TLA+ AI Linter (Microsoft GenAIScript, 2024)

- **What it is**: GenAI script that uses LLMs to lint TLA+ files, checking if prose comments are consistent with TLA+ definitions
- **Input**: TLA+ files with prose comments
- **Output**: Lint warnings about comment-definition inconsistencies
- **Machine-checkable?**: Partially -- LLM-based checking, not formal
- **Method**: LLM prompted as TLA+ expert to compare natural language comments against formal definitions
- **Source available?**: Yes, open-source GenAIScript case study
- **Claim verification**:
  - Claims: Can detect mismatches between prose and formal TLA+ definitions
  - Demonstrated: Working linter tool
  - Missing for our use: Reverse direction (checks existing specs against text, doesn't generate specs from text). But the text<->spec alignment checking is directly relevant to evaluation.

### D5: TLAi Challenge -- Grammar-Constrained TLA+ Generation (2025)

- **What it is**: Entry in the TLAi+ Challenge testing whether local LLMs can be constrained to produce valid TLA+ via grammar-based token restriction
- **Input**: Prompts describing desired TLA+ specifications
- **Output**: TLA+ specifications
- **Machine-checkable?**: Yes -- constrained to be syntactically valid
- **Method**: LlamaCpp GBNF syntax (context-free) + Guidance framework (context-sensitive) for token-level grammar enforcement
- **Source available?**: Presented at TLAi+ Challenge
- **Claim verification**:
  - Claims: Grammar-based constraints can reliably enforce TLA+ syntax and symbol definition
  - Demonstrated: Syntactic validity via constrained decoding; improved results with TLA+ documentation in prompts
  - Missing for our use: No NL understanding component -- prompts must already describe spec structure. Syntax enforcement is necessary but not sufficient.

### D6: LLMs Cannot Generate Valid TLA+/PlusCal (Shan 2024)

- **What it is**: Technical report testing multiple open-source LLMs on TLA+/PlusCal generation
- **Input**: Prompts asking for TLA+/PlusCal code
- **Output**: Attempted TLA+/PlusCal (all failed to parse)
- **Machine-checkable?**: No -- none of the outputs were parsable by SANY
- **Method**: Direct prompting of Llama3, Phi3, CodeCopilot, Mistral, CodeLlama; also tried explanation + reflection
- **Source available?**: Tech report from EPITA
- **Evaluation**: All models failed. Explanation and reflection did not help.
- **Claim verification**:
  - Claims: Open-source LLMs are insufficiently trained on TLA+/PlusCal
  - Demonstrated: Complete failure across 5 models
  - Missing for our use: Negative result, but important baseline. Shows why constrained decoding or fine-tuning is needed.

### D7: TLAiBench -- Benchmark for LLMs on TLA+ Tasks (2025)

- **What it is**: Dataset and benchmark suite for evaluating LLMs on TLA+ formal specification tasks
- **Input**: Logic puzzles and real-world scenario descriptions
- **Output**: TLA+ specifications (expected from LLMs being evaluated)
- **Machine-checkable?**: Yes -- standardized evaluation
- **Source available?**: https://github.com/tlaplus/TLAiBench
- **Claim verification**:
  - Claims: Standardized benchmark for LLM evaluation on TLA+ tasks
  - Demonstrated: Public repository with benchmark data
  - Missing for our use: Benchmark rather than system. Can be used to evaluate future text->TLA+ systems.

## Justification for "No Direct Text->TLA+ Work Found"

As of February 2026, based on 13 systematic searches across Google Scholar, arXiv, GitHub, ACM DL, IEEE Xplore, and venue-specific sources (FMCAD, CAV, ICSE, ASE, ACL, NeurIPS):

1. **No system takes free-form natural language and produces a machine-checkable TLA+ module.** The closest (Specula) takes source code as input.
2. **LLMs largely fail at generating valid TLA+ syntax** (Shan 2024), suggesting that without constrained decoding or fine-tuning, direct generation is unreliable.
3. **The TLA+ community recognizes this gap** -- the TLAi+ Challenge and TLAiBench were created specifically to spur progress.
4. **Strongest near-misses**: Specula (code->TLA+), SysMoBench (benchmark), grammar-constrained TLA+ generation (syntax only), and TLA+ proof automation (not generation).
